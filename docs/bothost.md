# Развёртывание ECHO на Bothost

## Почему возникал ModuleNotFoundError

Bothost монтирует исходники Git в `/app`. Прежнее окружение `/app/.venv`, созданное при сборке, скрывалось этим монтированием. Команда `python -m echo.main` выбирала системный `/usr/local/bin/python`, где пакет не установлен. Ошибка воспроизведена локально с таким же bind mount.

Приложение и его зависимости теперь установлены в `/opt/echo`, поисковые движки и инструменты — в прежних `/opt/sherlock`, `/opt/maigret`, `/opt/tools`. Код остаётся в `/app/src`. В корне добавлен `main.py`: при запуске системным Python он переключается на `/opt/echo/bin/python`, затем загружает пакет из `src`.

Официальное описание монтирования и настройки: [кастомный Dockerfile Bothost](https://bothost.ru/docs/custom-dockerfile), [точка входа](https://bothost.ru/docs/main-file-entrypoint), [переменные окружения](https://bothost.ru/docs/environment-variables), [постоянное хранилище](https://bothost.ru/docs/database-storage).

## Настройка в панели

1. Репозиторий: `https://github.com/Japhet17429475581/echo.git`, ветка `main`.
2. В дополнительных настройках включите **«Использовать собственный Dockerfile»**. Путь — `Dockerfile` из корня. Автогенерация не устанавливает весь набор изолированных движков и системных инструментов ECHO.
3. Команду оставьте из Dockerfile: `/opt/echo/bin/python -m echo.main serve`. При выборе файла запуска используйте корневой `main.py`, без `-m`. Для кастомного Dockerfile запуск задаётся его CMD, а не полем главного файла.
4. Сохраните изменения и выполните **новый деплой с пересборкой образа**. Обычный рестарт старого контейнера не исправляет окружение.

Обязательные переменные:

```env
ECHO_DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DATABASE?sslmode=require
ECHO_REDIS_URL=rediss://USER:PASSWORD@HOST:PORT/0
```

Вставьте свои настоящие PostgreSQL/Redis строки в панель, не в Git. Нужен Redis protocol URL, не HTTP REST endpoint. В Compose Redis запускается отдельно, а Bothost не поднимает сервисы из `compose.yaml`; строка `redis://redis:6379/0` здесь сама по себе Redis не создаёт.

Bothost передаёт Telegram-токен в `BOT_TOKEN`; ECHO его принимает. Непустой `ECHO_BOT_TOKEN` имеет приоритет. Для DeepSeek при необходимости задайте прежние `ECHO_AI_KEY`/`ECHO_AI_ENABLED`; эти данные не нужны для устранения ошибки импорта.

## Режим одного контейнера

`serve` применяет миграции, затем запускает существующие Telegram handlers и Worker в одном процессе и с общей папкой файлов. PostgreSQL-очередь, Redis-слоты, AI gateway, владение и лимиты остаются прежними. Если бот или worker завершается, второй также останавливается; платформа может перезапустить контейнер целиком.

В `serve` файловое хранилище по умолчанию `/app/data/echo`, чтобы использовать сохраняемую Bothost папку `data`. `ECHO_DATA_DIR` позволяет явно изменить путь. Каталог должен быть доступен контейнерному UID 10001 для записи. В Compose продолжают работать отдельные роли `bot`/`worker` с общим volume `/data/echo`; их команды не изменены.

Запускайте одну polling-копию с токеном. `serve` объединяет bot/worker, поэтому при выборе ресурсов учитывайте их совместное потребление и пиковую память инструментов; бюджет описан в [modules.md](modules.md). Это приложение с subprocess и системными библиотеками, успешный импорт не означает, что ему достаточно любого минимального тарифа.

## Проверка

После успешных миграций в журнале появляется `starting_bot_and_worker`. Проверка из терминала контейнера:

```sh
/opt/echo/bin/python -m echo.main health --worker
```

Команда проверяет БД, Redis и heartbeat worker. Она не проверяет доставку Telegram. Локальные тесты воспроизводят скрытие `/app/.venv`, запуск `/usr/local/bin/python /app/main.py --help`, миграции/worker с подменённым локальным Telegram polling и готовность всех шести инструментов. К аккаунту Bothost владельца автоматического доступа нет: окончательный деплой и доставка с его токеном проверяются после обновления в панели.
