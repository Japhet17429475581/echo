# Развёртывание ECHO на Bothost

## Почему возникал ModuleNotFoundError

Bothost монтирует исходники Git в `/app`. Перенос одного virtualenv из `/app/.venv` в `/opt/echo` оказался недостаточным: editable-установка всё ещё ссылалась на `/app/src`. Если содержимое `/app` заменено и `src/echo` недоступен, даже `/opt/echo/bin/python -m echo.main` выдаёт `ModuleNotFoundError`. Это воспроизведено локально с полностью скрытой `/app`.

Приложение теперь устанавливается обычным wheel через `uv sync --no-editable` в `/opt/echo`. В wheel входят код, миграции Alembic, изображения и файлы запуска движков и инструментов. Поисковые движки и библиотеки инструментов остаются в `/opt/sherlock`, `/opt/maigret`, `/opt/tools`. Импорт и ресурсы больше не зависят от содержимого `/app`. Корневой `main.py` переключает системный Python на `/opt/echo/bin/python` и использует установленный пакет; при локальной разработке поддерживается прежняя структура `src`.

Официальное описание монтирования и настройки: [кастомный Dockerfile Bothost](https://bothost.ru/docs/custom-dockerfile), [точка входа](https://bothost.ru/docs/main-file-entrypoint), [переменные окружения](https://bothost.ru/docs/environment-variables), [постоянное хранилище](https://bothost.ru/docs/database-storage).

## Настройка в панели

1. Репозиторий: `https://github.com/Japhet17429475581/echo.git`, ветка `main`.
2. В дополнительных настройках включите **«Использовать собственный Dockerfile»**. Путь — `Dockerfile` из корня. Автогенерация не устанавливает весь набор изолированных движков и системных инструментов ECHO.
3. Команду оставьте из Dockerfile: `/opt/echo/bin/python -m echo.main serve`. При выборе файла запуска используйте корневой `main.py`, без `-m`. Для кастомного Dockerfile запуск задаётся его CMD, а не полем главного файла.
4. Сохраните изменения и выполните **новый деплой с пересборкой образа**. Обычный рестарт старого контейнера не исправляет окружение.

Обязательные переменные:

```env
ECHO_DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DATABASE?sslmode=require
ECHO_REDIS_URL=rediss://USER:PASSWORD@HOST:PORT/0
```

Вставьте свои настоящие PostgreSQL/Redis строки в панель, не в Git. Нужен Redis protocol URL, не HTTP REST endpoint. В Compose Redis запускается отдельно, а Bothost не поднимает сервисы из `compose.yaml`; строка `redis://redis:6379/0` здесь сама по себе Redis не создаёт.

Bothost передаёт Telegram-токен в `BOT_TOKEN`; ECHO его принимает. Непустой `ECHO_BOT_TOKEN` имеет приоритет. Для DeepSeek при необходимости задайте прежние `ECHO_AI_KEY`/`ECHO_AI_ENABLED`; эти данные не нужны для устранения ошибки импорта.

## Режим одного контейнера

`serve` применяет миграции, затем запускает существующие Telegram handlers и Worker в одном процессе и с общей папкой файлов. PostgreSQL-очередь, Redis-слоты, AI gateway, владение и лимиты остаются прежними. Если бот или worker завершается, второй также останавливается; платформа может перезапустить контейнер целиком.

В runtime-образе файловое хранилище по умолчанию `/app/data/echo`, чтобы использовать сохраняемую Bothost папку `data`. `ECHO_DATA_DIR` позволяет явно изменить путь. Образ запускает небольшой bootstrap: он создаёт только приватные каталоги данных и временных файлов, назначает им UID/GID 10001 и права 0700, затем убирает дополнительные группы и запускает команду от `echo`. Родительская `/app/data` и существующие файлы рекурсивно не меняются. Это позволяет работать с примонтированной `/app/data`, принадлежащей root с правами 0755. Bootstrap выполняется через ENTRYPOINT — оставьте запуск из Dockerfile.

В Compose продолжают работать отдельные роли `bot`/`worker` с общим volume `/data/echo`. Compose явно задаёт UID/GID 10001 и путь volume, поэтому первоначального запуска от root там нет. Для запуска образа с `--user 10001:10001` или без возможностей CHOWN/SETUID/SETGID папки должны быть заранее доступны этому пользователю. Если подготовка каталога невозможна, процесс пишет безопасный код `startup_failed stage=data_directory error=PermissionError errno=13` и завершается; временное хранилище вместо постоянного автоматически не подставляется.

Запускайте одну polling-копию с токеном. `serve` объединяет bot/worker, поэтому при выборе ресурсов учитывайте их совместное потребление и пиковую память инструментов; бюджет описан в [modules.md](modules.md). Это приложение с subprocess и системными библиотеками, успешный импорт не означает, что ему достаточно любого минимального тарифа.

## Проверка

После успешных миграций в журнале появляется `starting_bot_and_worker`. Проверка из терминала контейнера:

```sh
/opt/echo/bin/python -m echo.main health --worker
```

Команда проверяет БД, Redis и heartbeat worker. Она не проверяет доставку Telegram. CI проверяет импорт с полностью скрытой `/app`:

```sh
docker run --rm --read-only --tmpfs /app:rw,nosuid,nodev,size=1m echo-bot:ci /opt/echo/bin/python -m echo.main --help
```

Также проверяются корневой launcher, миграции из wheel, запуск с root-owned хранилищем и worker с подменённым локальным Telegram polling. Smoke дожидается готовности всех шести инструментов и успешного полного цикла очистки. При сбое очистки журнал показывает этап (`heartbeat`, `capabilities`, `jobs`, `files`, `scratch`), класс ошибки, errno и SQLSTATE без сообщений исключений, SQL и секретов; остальные этапы продолжаются. К аккаунту Bothost владельца автоматического доступа нет: окончательный деплой и доставка с его токеном проверяются после обновления в панели.
